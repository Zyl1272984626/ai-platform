问题列表

1. 🔴 Critical — SEC002：AES使用ECB模式加密，且解密函数配置自相矛盾

文件: aes.js:15-25

问题描述:

  • encrypt 方法使用 CryptoJS.mode.ECB 模式（第15行），ECB对相同明文始终产生相同密文，存在模式泄露（pattern leakage）风险，攻击者可推断数据结构

  • decrypt 方法（第25行）指定了 iv: key 参数，但 ECB 模式**完全不使用 IV**，这是配置矛盾，说明开发者对加密模式理解有误

  • 密钥同时被当作 IV 使用也是加密反模式

    • // 第15行 - ECB模式不安全
    var encrypted = CryptoJS.AES.encrypt(srcs, key, {mode: CryptoJS.mode.ECB, padding: CryptoJS.pad.Pkcs7});
    // 第25行 - 指定了iv但ECB模式不使用iv，配置矛盾
    var decrypt = CryptoJS.AES.decrypt(word, key, {iv: key, mode: CryptoJS.mode.ECB, padding: CryptoJS.pad.Pkcs7});

    修复建议: 将模式改为 CBC 或 GCM，生成随机 IV 并与密文拼接传输：

    encrypt(key, word) {
      const keyBytes = CryptoJS.enc.Utf8.parse(key);
      const iv = CryptoJS.lib.WordArray.random(16);
      const encrypted = CryptoJS.AES.encrypt(
        CryptoJS.enc.Utf8.parse(word), keyBytes,
        { iv, mode: CryptoJS.mode.CBC, padding: CryptoJS.pad.Pkcs7 }
      );
      return iv.toString() + encrypted.toString(); // IV + 密文
    }

    2. 🔴 Critical — SEC003：RSA公钥硬编码 + 加密密钥明文传输 + isProd硬编码为false

    文件: constant.js:3-5, security-flow.js:36-38, security-flow.js:76-78

    问题描述:

  • **RSA公钥硬编码**（constant.js:5）：公钥直接写在源码中，无法轮换，且被所有客户端共享，一旦泄露无法更换

  • **isProd硬编码为false**（constant.js:3）：注意原始的 process.env.NODE_ENV === 'production' 被注释掉了，当前 isProd = false，这意味着**所有环境（包括生产）的加密都被跳过**！encryptPost 第38行和 encryptGet 第78行在 !isProd 时直接返回明文数据

  • **AES密钥明文包含在返回对象中**（security-flow.js:36, security-flow.js:76）：aesKey 字段以明文形式返回，虽然 axios-handler.js 中未使用该字段发送到服务端，但它作为对象属性在内存中可被访问，且如果后续代码引用就会泄露密钥

    • // constant.js:3 - 生产环境加密被完全禁用！
    export const isProd = false;
    // 原本的正确逻辑被注释：
    // export const isProd = process.env.NODE_ENV === 'production';
    // security-flow.js:38 - 非生产环境直接传明文
    aesData: this.hasFile(data) ? data : (isProd ? aesWord : data)  // → 永远是data
    // security-flow.js:36 - aesKey明文暴露
    aesKey: aesKey,   // 不应包含在返回对象中

    修复建议:

  • 恢复 isProd = process.env.NODE_ENV === 'production' 或从后端动态获取加密开关

  • 从 encryptPost/encryptGet 的返回值中移除 aesKey 明文字段

  • RSA公钥通过 API 动态获取，而非硬编码

    问题列表

    安全性

    #### 1. 🔴 Critical — SEC001: dangerouslyUseHTMLString 渲染未净化的后端错误消息（XSS）

  • **文件**: config.ts:127-135, config2.js:92-102

  • **问题**: 错误消息 errorMsg 和 url 直接拼接进 HTML 字符串 <p>${errorMsg}！</p>，然后通过 dangerouslyUseHTMLString: true 渲染。后端返回的 data.message 或请求 URL 如果被攻击者控制（如构造恶意 URL 或后端返回注入内容），可以注入任意 HTML/JS。

  • **修复建议**: 使用纯文本通知，移除 dangerouslyUseHTMLString；如需格式化，用 DOMPurify 净化内容后再渲染。

    • #### 2. 🔴 Critical — SEC003: RSA 公钥硬编码 + isProd 硬编码为 false 导致加密完全失效

  • **文件**: security/constant.js:3-5, security/security-flow.js:38, security/security-flow.js:78

  • **问题**:

    • 1. isProd = false 被硬编码，导致 security-flow.js:38 和 :78 中所有加密分支被短路——isProd ? aesWord : data 始终返回明文 data，整个加密体系形同虚设。
    2. RSA 公钥硬编码在前端源码中，任何人都可以查看。
    3. encryptPost 返回对象包含 aesKey 明文字段 (security-flow.js:36)，攻击者可在运行时直接获取 AES 密钥。
  • **修复建议**:

    • - 将 isProd 改为读取 import.meta.env.MODE === 'production' 动态判断。
    - 通过 API 动态获取 RSA 公钥。
    - 不要在返回对象中包含 aesKey 明文。

    #### 3. 🔴 Critical — SEC002: AES 使用 ECB 模式不安全 + 加解密配置矛盾

  • **文件**: security/aes.js:15, security/aes.js:25

  • **问题**:

    • 1. 加密使用 ECB 模式 (CryptoJS.mode.ECB)，相同明文产生相同密文，存在模式泄露风险。
    2. decrypt 方法指定了 iv: key 参数，但 ECB 模式不使用 IV，配置矛盾说明开发者对加密模式理解不足。
  • **修复建议**: 改用 CBC 或 GCM 模式，使用随机 IV 并与密文一起传输。

    • #### 4. 🔴 Critical — SEC005: Token 从 URL 参数读取存在泄露风险

  • **文件**: config.ts:17, utils/browser.js:87-91

  • **问题**: getParam("token") 从 URL query string 读取认证 token。URL 参数会被记录在浏览器历史、服务器访问日志、Referer 头中，存在 token 泄露风险。此外 getParam 使用已废弃的 unescape() 函数（browser.js:90）。

  • **修复建议**: 使用 HttpOnly Cookie 或安全的 token 交换流程传递 token，避免通过 URL 参数传递敏感信息。

    • #### 5. 🟡 Warning — AES 密钥内存无限累积

  • **文件**: security/axios-handler.js:3,23

  • **问题**: aesKeyHash 是模块级对象，每次请求都写入一条 aesKeyHash[encrypt.rsaAesKey] = encrypt.aesKey（第23行），但从未清理。在长时间运行的 SPA 中，内存会持续增长。

  • **修复建议**: 响应处理后删除已使用的密钥 delete aesKeyHash[config.headers['tk']]，或使用 LRU 缓存。

    错误处理

    #### 6. 🔴 Critical — ERR003: 响应拦截器 location.reload() 后未 reject Promise

  • **文件**: config.ts:69-72,74-77, config2.js:34-36,41-43

  • **问题**: 当 sessionstatus === 'timeout' 时执行 location.reload() 并 return;（返回 undefined），但没有 return Promise.reject()。这意味着调用方的 .then() 仍会以 undefined 执行，可能引发后续逻辑错误。

  • **修复建议**: 在 location.reload() 后添加 return Promise.reject(new Error('session timeout'))。

    • #### 7. 🟡 Warning — ERR001: 空 catch 块吞没异常

  • **文件**: config.ts:28-30

  • **问题**: try { ... } catch (e) { // ignore } 静默吞没了 localStorage 读取异常，可能是 QuotaExceededError 或 SecurityError（隐私模式），无法排查问题。

  • **修复建议**: 添加 console.warn('Failed to read token from localStorage:', e) 或上报到监控。

    • #### 8. 🟡 Warning — 响应成功拦截器未覆盖非200状态码

  • **问题**: 成功回调仅处理 status === 200 的情况，但 HTTP 2xx 系列状态码（201、204 等）都会进入成功回调。非200的2xx响应会走到函数末尾隐式返回 undefined，调用方拿到 undefined。

  • **修复建议**: 添加默认 return response 或 return Promise.reject(response) 处理其他2xx状态码。

  • **修复建议**: 将 return console.error(...) 改为先 console.error，再 return '重复请求：' + error.message。

    • #### 10. 🔵 Info — request3.js 使用已废弃的 unescape()
