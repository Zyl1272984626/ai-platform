# 代码审查中断恢复方案调研

## 背景

代码审查使用 `@anthropic-ai/claude-code` SDK 的 `query()` 函数调用 Claude 分析源码。当遇到 429 限流、网络中断、进程崩溃等情况时，整个对话上下文丢失，必须从头开始。对于大型项目（十几个模块、上百个文件），这意味着重复读文件、重复分析，浪费大量时间和 Token。

## 现状分析

### 当前运行方式

```
用户点击「开始测试」
  → 前端 POST /run
  → 后端创建 TestSuite，fire-and-forget 调 executeTestRun()
  → executeTestRun() 入队，等并发位
  → executeTestRunInternal() 发 test:start 事件
  → runCodeReview() 按模块逐个审查：
      for (每个模块) {
        query({ prompt: 审查prompt })  ← 全新对话，无历史
        → Claude 读文件、分析、输出报告
        → 保存该模块结果
      }
  → 合并报告，发 test:done 事件
```

每次 `query()` 都是全新对话，没有任何上下文延续能力。

### 中断场景

| 场景 | 当前后果 | 期望行为 |
|------|---------|---------|
| 429 限流 | 当前模块报错，后续模块可能继续（但如果 abortController 被触发则全部中断） | 等限流恢复后继续 |
| 网络闪断 | query() 抛异常，模块标记为 error | 自动重试该模块 |
| 用户手动停止 | abortController 中断，所有未完成模块标记 error | 下次只跑未完成的模块 |
| 服务器重启 | 内存状态全丢，磁盘上模块状态可能不一致 | 重启后可恢复进度 |

## SDK 原生支持

### `options.continue: boolean`

恢复**最近一次**对话（按 cwd 目录匹配）。

```typescript
query({
  prompt: '请继续之前的审查',
  options: {
    continue: true,    // ← 恢复最近一次对话
    cwd: projectPath,  // 按 cwd 匹配
  }
})
```

- 优点：最简单，一个参数
- 缺点：只能恢复**最近一次**，如果用户跑了多个项目会串

### `options.resume: string`（推荐）

恢复**指定 session** 的对话。session_id 从 `query()` 返回的每条 SDKMessage 中获取。

```typescript
// 第一次调用，捕获 session_id
const response = query({ prompt: '审查代码', options: { cwd: projectPath } })
for await (const msg of response) {
  if (msg.type === 'system') {
    sessionId = msg.session_id  // ← 保存这个
  }
  // ... 处理消息
}

// 中断后恢复
const response2 = query({
  prompt: '请继续之前的审查',
  options: {
    resume: sessionId,   // ← 传入之前保存的 session_id
    cwd: projectPath,
  }
})
```

- 优点：精确恢复指定会话，不会串
- 缺点：需要自己持久化 session_id

### `options.resumeSessionAt: string`

配合 `resume` 使用，从**指定消息位置**恢复。

```typescript
query({
  prompt: '从这里继续',
  options: {
    resume: sessionId,
    resumeSessionAt: messageId,  // ← 从这条消息之后继续
  }
})
```

- 适合：对话很长，只想恢复后半段

### `options.forkSession: boolean`

配合 `resume` 使用，恢复时创建新 session（不修改原始会话）。

```typescript
query({
  prompt: '请继续审查',
  options: {
    resume: sessionId,
    forkSession: true,  // ← 新 session，不影响原会话
  }
})
```

- 适合：想保留原始对话完整性

## 三种方案对比

### 方案 A：模块级断点续传（当前架构微调）

**原理**：利用现有按模块执行的架构，记录每个模块的完成状态。中断后重新跑时跳过已完成的模块。

```
运行中：
  模块 A ✅ 已完成 → 结果已保存
  模块 B 💥 中断   → 标记为 interrupted
  模块 C ⬜ 未开始

恢复时：
  模块 A → 跳过（结果已存在）
  模块 B → 重新跑（全新 query，无上下文）
  模块 C → 正常跑
```

**改动范围**：
- `test-runner.ts`：模块完成后立即持久化状态到 JSON
- 前端：增加「恢复中断的审查」按钮
- 恢复时读取 JSON，过滤掉已完成的模块

**优点**：
- 改动最小，不依赖 SDK 新特性
- 逻辑简单，容易理解和维护
- 已完成模块不会浪费 Token 重跑

**缺点**：
- 中断的模块（模块 B）必须**从头重跑**，之前读的文件、分析全部丢弃
- 如果单个模块很大（几十个文件），重跑代价仍然高
- 无法真正"续接"对话上下文

### 方案 B：SDK resume 会话恢复（推荐）

**原理**：利用 SDK 原生的 `resume` 功能，保存 session_id，中断后用 `resume` + `forkSession` 恢复对话上下文。

```
首次运行：
  query({ prompt: '审查模块B', options: { cwd } })
  → 捕获 session_id = "abc-123"
  → 中途 429 断了...

恢复运行：
  query({
    prompt: '请继续之前的审查，从你中断的地方继续',
    options: {
      resume: "abc-123",   // 恢复这个会话
      forkSession: true,   // 新 session，不污染原会话
      cwd: projectPath,
    }
  })
  → Claude 拥有之前的全部上下文（读过的文件、分析过的代码）
  → 直接继续，不需要重新读文件
```

**改动范围**：
- `test-runner.ts`：
  - 每次 `query()` 开始时捕获 `session_id`
  - 中断时保存 `{ suiteId, moduleId, sessionId, partialOutput }` 到 JSON
  - 恢复时读取 JSON，用 `resume: sessionId` 重新调用
- 前端：增加「恢复」按钮
- `config.ts`：无改动

**优点**：
- **真正续接上下文**：Claude 记得之前读过的文件，不需要重新读取
- **节省 Token**：不重复发送之前的内容
- **节省时间**：跳过已分析的部分
- SDK 原生支持，不需要自己维护消息历史

**缺点**：
- 依赖 Claude Code 内部的会话存储（磁盘上的 transcripts），如果 transcripts 被清理则无法恢复
- `forkSession` 会创建新 session，每次恢复消耗一个新的 session 空间
- 需要验证：恢复后的 prompt 质量是否足够让 Claude 正确续接

### 方案 C：混合方案（A + B）

**原理**：模块级断点 + SDK resume 结合。已完成的模块跳过，中断的模块用 resume 恢复。

```
恢复时：
  模块 A ✅ → 跳过
  模块 B 💥 → resume(sessionId_B) + forkSession  ← 恢复上下文
  模块 C ⬜ → 全新 query()
```

**优点**：最完善，两种机制互补

**缺点**：改动范围最大，需要持久化每个模块的 session_id

## 方案对比总结

| 维度 | A 模块级断点 | B SDK resume | C 混合方案 |
|------|------------|-------------|-----------|
| 改动范围 | 小 | 中 | 大 |
| 中断模块是否重跑 | 是（从头） | 否（续接） | 否（续接） |
| Token 节省 | 部分（跳过已完成） | 显著（上下文保留） | 最大 |
| 恢复速度 | 中断模块仍慢 | 快 | 快 |
| 实现复杂度 | 低 | 中 | 高 |
| 依赖风险 | 无 | transcripts 清理后失效 | 同 B |

---

## 推荐方案

**先做 A，再做 B，最终到 C。分步实施：**

### 第一步：方案 A（快速见效）

- 每个模块完成后立即持久化结果到 JSON
- 前端增加「恢复审查」功能
- 估算改动：1-2 小时

### 第二步：方案 B（核心优化）

- 捕获并持久化 session_id
- 中断模块用 resume 恢复
- 估算改动：2-3 小时

### 第三步：方案 C（完善体验）

- 自动检测中断状态
- 前端一键恢复，后端智能选择跳过/续接
- 估算改动：1 小时（在 A+B 基础上）

## 附录：SDK Options 中断恢复相关字段

```typescript
export type Options = {
  // ... 其他字段 ...

  /** 恢复最近一次对话（按 cwd 匹配） */
  continue?: boolean;

  /** 恢复指定 session 的对话，值为 session_id */
  resume?: string;

  /** 恢复时从指定消息位置继续，配合 resume 使用 */
  resumeSessionAt?: string;

  /** 恢复时创建新 session，不修改原始会话，配合 resume 使用 */
  forkSession?: boolean;
}
```

每条 SDKMessage 都包含 `session_id` 字段，可在首次调用时捕获并持久化。
