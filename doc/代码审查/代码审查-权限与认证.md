# 代码审查报告 — 权限与认证

## 综合评分（0-100）
**58 / 100**

本模块是系统安全的核心防线，存在多个中高危安全问题。路由守卫在两个入口（index / setting-system）之间存在大量重复代码，企微 OAuth 重定向存在开放重定向风险，`localStorage` 中存储的 `originalUrl` 可被攻击者注入实现钓鱼，`useLoginTo` 中直接使用 `location.replace(originalUrl)` 跳转未做校验。整体安全意识需加强，代码架构需去重。

## 问题列表

### P0 — Critical

#### 1. [Critical] SEC007 — 开放重定向漏洞：localStorage 中的 originalUrl 未校验即用于跳转
- **文件**: `E:/workhome/agent/frontend/src/hooks/login/useLoginTo.ts` 第 5-10 行
- **相关文件**: `permission.js` 两处（index 第 50 行、setting-system 第 29 行）均读取 `localStorage.getItem('originalUrl')` 后调用 `routeTo()`
- **问题描述**: `originalUrl` 由 `localStorage.setItem('originalUrl', currentUrl)` 写入，其中 `currentUrl = window.location.href`。`localStorage` 可被同源的任何脚本写入（包括 XSS），也可被开发者工具手动篡改。`useLoginTo.ts` 第 10 行直接执行 `location.replace(originalUrl)` 跳转，未对 URL 做任何域名校验或白名单过滤。攻击者若通过 XSS 或其他方式向 `localStorage` 注入恶意 URL（如 `https://evil.com`），用户登录后会被静默重定向到钓鱼站点。
- **修复建议**:
  1. 在 `routeTo()` 中对 `originalUrl` 做域名校验，只允许同源跳转：
     ```javascript
     try {
       const url = new URL(originalUrl, window.location.origin);
       if (url.origin !== window.location.origin) {
         console.warn('非法重定向 URL，已忽略');
         localStorage.removeItem('originalUrl');
         return;
       }
     } catch (e) {
       localStorage.removeItem('originalUrl');
       return;
     }
     ```
  2. 可选：改用 `sessionStorage` 存储 originalUrl（生命周期更短，关闭标签页即清除）。

#### 2. [Critical] SEC007 — 企微 OAuth 重定向：requestUrl 参数通过 URL 传递当前页面地址
- **文件**: `E:/workhome/agent/frontend/src/pages/index/permission.js` 第 31-32 行
- **问题描述**: `window.location.href = '../weixin/oauth/authorize?agentId=${to.query.agentId}&requestUrl=${requestUrl}'`，其中 `requestUrl = encodeURIComponent(window.location.href)`。这里将完整的当前页面 URL（含所有 query 参数、hash）编码后拼接到重定向地址。如果当前页面 URL 中包含敏感参数（如 token、sessionId 等），它们会被传递到后端 OAuth 接口，可能出现在服务端日志、Referer 头或浏览器历史记录中。同时 `to.query.agentId` 直接从 URL 参数获取并拼接到重定向 URL，未做格式校验。
- **修复建议**:
  1. 审查 `window.location.href` 中是否可能包含 token 等敏感参数，如果有则应在编码前移除。
  2. 对 `agentId` 做格式校验（如只允许字母数字）后再拼接到 URL。
  3. 考虑使用 `location.assign()` 代替直接赋值 `location.href`，语义更清晰。

#### 3. [Critical] SEC004 — SSE 流式请求从 localStorage 直接读取 token 传递
- **文件**: `E:/workhome/agent/frontend/src/pages/setting-system/views/msg/msg-chat-panel.vue` 第 172 行
- **问题描述**: `const token = window.localStorage.getItem('token') || ''`，然后通过 `fetch` 请求头传递。`localStorage` 中的 token 可被同源页面中任何 JS 代码读取（包括被注入的第三方脚本/XSS payload），存在 token 被窃取的风险。另外，token 存储在 `localStorage` 中没有过期机制，关闭浏览器后仍然存在。
- **修复建议**:
  1. 优先使用 HttpOnly + Secure + SameSite cookie 存储 token，避免 JS 可直接访问。
  2. 如果必须在前端存储 token，优先使用 `sessionStorage`（标签页关闭即清除）而非 `localStorage`。
  3. 确认 SSE 请求是否可通过 cookie 认证（`fetch` 的 `credentials: 'include'`）。

### P1 — High

#### 4. [High] FW005 — 路由守卫异步操作缺少 try-catch 异常处理
- **文件**: `E:/workhome/agent/frontend/src/pages/index/permission.js` 第 39-43 行
- **文件**: `E:/workhome/agent/frontend/src/pages/setting-system/permission.js` 第 19-23 行
- **问题描述**: `api.get("common/auth/loginStatus", {})` 和 `api.get("common/auth/userinfo", {keys: 'roles'})` 均为异步网络请求，但外层 `router.beforeEach` 回调中没有 try-catch 包裹。如果网络请求失败（超时、服务器 500、网络断开），会抛出未捕获的 Promise 异常，导致路由导航中断，用户看到空白页面，NProgress 进度条永远不结束（没有调用 `NProgress.done()`）。
- **修复建议**:
  ```javascript
  router.beforeEach(async (to, from, next) => {
    NProgress.start();
    try {
      // ... 现有逻辑
    } catch (error) {
      console.error('路由守卫异常:', error);
      NProgress.done();
      next('/login'); // 或展示错误页面
    }
  });
  ```

#### 5. [High] ERR001 — 登录状态重复设置
- **文件**: `E:/workhome/agent/frontend/src/pages/index/permission.js` 第 41 行和第 43 行
- **文件**: `E:/workhome/agent/frontend/src/pages/setting-system/permission.js` 第 20 行和第 22 行
- **问题描述**: `state.set("isLogin", true)` 在两个文件中都被调用了两次（一次在 loginStatus 返回 true 之后，一次在 userinfo 返回之后），属于冗余代码。虽然不影响功能，但表明代码是复制粘贴产物，增加了维护成本。
- **修复建议**: 删除重复的 `state.set("isLogin", true)` 调用，只在 userinfo 成功后设置一次。

#### 6. [High] FW005 — 两个入口的路由守卫代码几乎完全重复
- **文件**: `E:/workhome/agent/frontend/src/pages/index/permission.js` 全文
- **文件**: `E:/workhome/agent/frontend/src/pages/setting-system/permission.js` 全文
- **问题描述**: `setting-system/permission.js` 与 `index/permission.js` 的路由守卫逻辑几乎完全相同（仅缺少企微 OAuth 逻辑和 appId 设置），属于严重的代码重复。未来修改鉴权逻辑时极易遗漏其中一个入口，造成安全漏洞。
- **修复建议**: 将公共的路由守卫逻辑抽取为独立的工具函数/模块，两个入口各自引入并扩展差异化部分（如 index 入口的企微 OAuth 逻辑）。

#### 7. [High] SEC004 — 全局 state/user/roles 等敏感信息通过 localStorage 持久化（推断）
- **文件**: 两个 `permission.js` 中的 `state.set("user", ...)` / `state.set("roles", ...)`
- **问题描述**: `state.set` 如果底层使用 localStorage 持久化（结合 `state.get` 使用模式判断），则用户信息、角色信息被持久存储在 localStorage 中。即使关闭浏览器后这些数据仍然存在，XSS 攻击可以读取所有用户信息。此外，角色信息可被手动篡改来伪造管理员权限（如修改 roles 数组中的 `codeX` 为 `ADMIN`）。
- **修复建议**:
  1. 确认 `state` 的持久化策略，敏感数据不应持久化到 localStorage。
  2. 角色权限判断应由后端每次请求时校验，前端只做展示级别控制。
  3. `isAdmin` 的判断逻辑依赖 `role.codeX === "ADMIN"`，应确保后端接口是真正的权限控制点。

#### 8. [High] PERF003 — 每次路由跳转都重新请求 loginStatus 和 userinfo
- **文件**: `E:/workhome/agent/frontend/src/pages/index/permission.js` 第 39-42 行
- **文件**: `E:/workhome/agent/frontend/src/pages/setting-system/permission.js` 第 19-22 行
- **问题描述**: 当 `user.isLogin()` 返回 false 时（首次访问或刷新页面），每次路由跳转都会调用 `loginStatus` 接口，然后在 loginStatus 返回 true 后立即再调用 `userinfo` 接口，造成两次网络请求。虽然登录后会 `state.set("isLogin", true)` 使后续路由跳过这些请求，但首次加载时的双请求仍有优化空间。
- **修复建议**: 考虑后端合并 loginStatus + userinfo 为一个接口，减少一次网络往返。

#### 10. [Medium] MNT002 — `permission.js` 使用 JS 而非 TS，与项目其他模块风格不一致
- **文件**: 两个 `permission.js` 文件
- **问题描述**: 项目使用 Vue 3 + TypeScript（`permiss.ts` 就是 TS 文件），但路由守卫的核心文件 `permission.js` 使用 JavaScript，缺少类型注解和编译期类型检查。考虑到这是权限核心模块，类型安全尤为重要。

#### 11. [Medium] ERR002 — 未处理 NProgress.done() 的调用
- **文件**: 两个 `permission.js` 文件
- **问题描述**: `NProgress.start()` 在路由守卫开始时调用，但在代码中多处通过 `next()` / `location.href` / `location.replace` 离开当前导航，未显式调用 `NProgress.done()`。虽然 Vue Router 在导航完成后理论上会触发 `router.afterEach`（通常在那里调用 `NProgress.done()`），但当使用 `location.href` / `location.reload()` 直接跳转时不会触发 afterEach 钩子，可能导致进度条卡住。
- **修复建议**: 在所有 `location.href` 赋值和 `location.reload()` 之前调用 `NProgress.done()`。

#### 12. [Medium] SEC004 — 企微 OAuth 使用 sessionStorage 标记存在并发标签页问题
- **文件**: `E:/workhome/agent/frontend/src/pages/index/permission.js` 第 28-36 行
- **问题描述**: 使用 `sessionStorage.getItem('wecom_oauth_returned')` 标记是否已完成 OAuth 回调。`sessionStorage` 是标签页隔离的，如果用户在企微中打开多个标签页访问同一移动端路由，每个标签页都会独立触发 OAuth 流程，不会互相干扰（这其实是正确的）。但标记只设置为 `'1'`，如果 OAuth 回调失败（如后端异常），标记已被设置，用户再次访问时会跳过 OAuth 直接触发 loginStatus 检查，可能陷入未登录死循环（loginStatus 返回 false -> location.href = getLogoutUrl() -> 再次跳回 -> ...）。
- **修复建议**: 在 OAuth 回调失败时清除 `wecom_oauth_returned` 标记，或在 loginStatus 返回 false 时检查是否为企微环境并重试 OAuth。

#### 13. [Medium] FW001 — appId 从路由参数获取后设为全局 header，但未做合法性校验
- **文件**: `E:/workhome/agent/frontend/src/pages/index/permission.js` 第 21-22 行
- **问题描述**: `let appId = to.params.appId; setGlobalHeader('appId', appId);` 直接将路由参数作为全局 HTTP header 设置，未做任何格式校验或白名单过滤。如果 appId 包含特殊字符（如换行符 `\r\n`），可能导致 HTTP header 注入（CRLF 注入）。
- **修复建议**: 对 appId 做格式校验（如只允许字母、数字、下划线、短横线），拒绝非法值。

#### 14. [Medium] FW005 — permiss.ts 中 init() 方法体被完全注释掉，hasUrl() 使用过时数据
- **文件**: `E:/workhome/agent/frontend/src/api/permiss.ts` 第 51-59 行、第 77-79 行
- **问题描述**: `permiss.init()` 方法体被完全注释掉（第 52-58 行），导致 `urlHash` 永远为空对象 `{}`。因此 `hasUrl(path)` 方法永远返回 `false`，权限校验形同虚设。虽然 `getUrls()` 方法通过 `state.get('resources')` 实时获取数据可以工作，但 `hasUrl()` 与 `init()` 的逻辑不一致，表明权限模块可能处于未完成状态。
- **修复建议**: 要么恢复 `init()` 方法体并确保调用链完整，要么删除 `hasUrl()` / `init()` 等无效代码，统一使用 `getUrls()` 的实时查询方式。

## 总结

### 核心风险

1. **开放重定向（最严重）**: `localStorage` 中的 `originalUrl` 被直接用于 `location.replace()` 跳转，未做域名校验。同源下任何 XSS 漏洞都可被利用来将用户重定向到恶意站点。这是一个 P0 级别的安全缺陷。

2. **Token 存储与传输风险**: Token 存储在 `localStorage`（JS 可直接读取），通过 fetch header 明文传递给 SSE 接口。一旦存在 XSS 漏洞，token 即可被窃取。应迁移到 HttpOnly cookie 方案。

3. **路由守卫无异常处理**: 核心鉴权流程中的网络请求完全没有 try-catch 保护，一旦后端异常或网络中断，用户将看到空白页面且无法自行恢复。

4. **权限校验模块半废弃**: `permiss.ts` 中 `init()` 被注释、`hasUrl()` 永远返回 false，表明前端菜单级权限控制可能并未真正生效。安全控制应主要依赖后端，前端的 `isAdmin` 判断仅用于 UI 展示。

### 改进优先级建议

| 优先级 | 改进项 |
|--------|--------|
| **立即** | 修复 originalUrl 开放重定向，添加域名校验 |
| **立即** | 路由守卫添加 try-catch 异常处理 |
| **短期** | 合并两个 permission.js 为统一模块，消除重复 |
| **短期** | 审查 token 存储方案，迁移到 HttpOnly cookie |
| **中期** | 将 permission.js 迁移为 TypeScript |
| **中期** | 清理 permiss.ts 中废弃代码，明确权限模块职责 |
